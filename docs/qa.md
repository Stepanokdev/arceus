# Testing the platform

Off by default (`qa.enabled: false`). With it on, the agent tests the whole platform in a headless browser by your instructions and writes a report per run. Nothing goes through the issue tracker: no ticket, no comment; what to do about a finding is yours to decide.

**Scenarios.** Tests are organised as scenarios: any number of named test runs, each with its own instructions and its own schedule. "Smoke" on weekdays at 07:00, "Regression" on Saturday at 02:00, "Payments" only by hand. They live in the runner's database, so one made or changed in the console (**Test runs**, [console.md](console.md)) or with `arceus-runner qa scenario` counts on the runner's next pass, without a restart. At most `qa.max_scenarios` (20) exist at once. A deleted scenario stops running and leaves the list; its number is never given to another one, so its past runs and reports keep its name.

**The instructions.** A file per scenario: the platform's URL, its test accounts and what to test, in any shape. The first scenario, "Main", reads `qa.instructions` (default `~/arceus/data/qa/instructions.md`, next to the secrets). The `runner` phase copies [qa-instructions.example.md](../config/qa-instructions.example.md) there once and never overwrites it. Every later scenario has its own file beside it, `scenarios/<n>.md`, written when the scenario is made. Text inside HTML comments never reaches the agent, so the example counts as empty until you write the instructions: `arceus-runner check` fails on any scenario whose file is empty or unreadable with `qa` on, and a run of it reports it had no instructions. The runner adds how to work and how to report, and names the scenario in the brief. A run keeps the text it started with, so editing the file never changes a run under way.

**Starting a run.** In the console, **Run now** beside a scenario. On the server, `arceus-runner qa run --scenario <n>` queues one and prints its number (with only one scenario, `--scenario` can be left out); `qa status` lists the latest runs with their scenario; `qa stop [n]` stops a queued or running one (its report keeps what it found). `qa scenario list` shows every scenario with its schedule and file; `qa scenario add NAME [--days mon,fri --at 07:30]`, `qa scenario set N [--name …] [--days …] [--at …] [--by-hand]` and `qa scenario delete N` do what the console does, for an install without it.

**When scenarios run by themselves.** A scenario with days and a time is queued on those days at that time, in `schedule.timezone`; one with neither runs only when someone starts it, and one with only days or only a time is refused when saved. A scheduled time is queued once, also across restarts; one missed by more than an hour is not made up. A scenario's time that comes while a run of that same scenario is queued or under way is skipped. Runs of different scenarios queue behind each other: two scenarios due at the same minute are both queued and run one after the other, so the second starts when the first is over, which can be hours after its time. In the shared workspace a queued run also goes before new tickets, so several scenarios queued at once hold tickets back for as long as they take together: give long scenarios times when no tickets are expected, or give test runs a folder of their own (below), and tickets no longer wait for them. A run of a scenario deleted before it started closes without starting and says so; one under way finishes by what it was given.

**Upgrading from one instructions file.** The update makes scenario 1, "Main", from what there was: it reads `qa.instructions`, and the first time the runner starts it is given `qa.schedule`, once. From then on `qa.schedule` is not read, and `arceus-runner check` asks to remove it. Past runs become runs of "Main".

**How it runs.** A run is the Bulava task `qa-<n>`. Without `qa.workspace` it holds the shared workspace from start to end, and a queued run goes before new tickets. Every repository is put on a local branch `arceus-qa/<n>` at its default branch as last fetched, so the agent can name the file and line it suspects; it changes no code. A repository with uncommitted work (a ticket waiting on people) is left as it is and read with `git show`. Afterwards every repository goes back where it was. Past `qa.timeout` (8 h) the run is stopped and reported as unfinished. The run's clock starts when it is prepared, and its times are fixed then: the time it is stopped and the time its agent stops testing are kept with the run, so the brief, the runner's stop and the console's page give the same times, and a `qa.timeout` changed later applies only to runs that start after it.

**Beside tickets.** With `qa.workspace` set to a folder beside the workspace (`~/arceus/qa-workspace`), a test run works there instead and a ticket goes on at the same time: a run starts while a ticket works, and a ticket starts, or is taken up again, while a run works. One test run at a time still: runs of other scenarios wait for the one under way. The folder holds two: `home`, the small git project Bulava runs the agent in (its `AGENTS.md`, the agent's report folder, the report's links), and `repos`, beside it, the code. When a run starts, each repository's default branch is fetched from the code host into a ref of the run's own (`refs/arceus/qa-<n>`) in the workspace's clone and checked out in `repos/<repository>` at that commit, detached, as a repository of its own that borrows the clone's objects instead of copying them (`git clone --shared`, its remote removed). So the folder holds only the checked-out files, not a second copy of every repository, and nothing a ticket's agent relies on moves in the clone: its branch, index, files, `origin/*`, `FETCH_HEAD` and stash stay as they were, no branch is made there, and whatever git the test run's agent runs in its checkout (a stash, a branch, a commit) stays in that checkout. The checkouts are read, never changed. They are read-only on disk, their git metadata too, so a shell command that writes there fails, as does a `git stash`, branch or commit. They are outside the engine's project and not listed as writable, so the engine also refuses its file-editing tools there. `AGENTS.md` and the brief say so, and the agent writes only in its report folder. The agent runs as the same system user as a ticket's: one that deliberately made a checkout writable again could change it, and could write into the ticket's workspace by its path. Claude Code's own sandbox for shell commands would close that, but on Ubuntu 24.04 it needs nested user namespaces that the system restricts by default, so it is not used; the boundary for that is the VM ([security.md](security.md)). The run reads the code host's default branch as it is when the run starts, even when the workspace last fetched it days ago. When the run is over the checkouts and the refs go, with anything the agent left in them; the folder stays for the next run. A run keeps the folder it was prepared in to its end, so changing `qa.workspace` touches only runs that start after. A run that was under way in the shared workspace when the key was set keeps holding it until it ends. When the console asks the engine to restart, neither tickets nor test runs start until it has.

**The folder is the runner's.** The runner removes things in `qa.workspace`, so it uses only a folder that does not exist yet, an empty one, or one with its mark, `.arceus-folder`, which it writes there the first time. A folder with other files and no mark, a link, or a file is refused: every run queued then closes as unfinished, saying why, and `arceus-runner check` fails on it. `home` and `repos` must be folders of their own inside it: a link in place of either is refused when a run is prepared, and found again before anything is written, read, removed or stopped there, as is a link anywhere on the way to a checkout or to the run's report folders (`.arceus`, `.arceus/qa`, `artifacts`), and a `home/.git` that is not the home's own git folder (a link, a `.git` file naming another repository's, or a `commondir` sharing another's refs and config; git itself is asked which folders it uses), which would send the runner's git commands into someone else's metadata. A run whose folder was replaced so while it works is resumed and reviewed no further: nothing more is handed to the engine by that path, its worker is ended by its session's kept name, its report is not read, and it closes saying why. Before it removes anything there at the end of a run it looks again; a folder replaced or moved meanwhile, or one with such a link, is left as it is, and only the run's refs go from the clones. A run is then stopped by its session's kept name, never by a path that may now lead to a ticket's folder.

**Crashes and stops.** Each repository a run fetches is named in its record before the ref that keeps its commit is made, and the commit after; a ref of the run's own name found after a crash in between is taken as the commit chosen. So a run cut short while it is being prepared (the code host stopped answering, the runner restarted) goes on with the same commits, even when main moved on meanwhile, and a run stopped before it started takes away every ref it made, also of a repository that left the group since. A run whose time ran out while the engine was busy is never dispatched late: the time is checked again right before the engine is asked. A dispatch the engine refuses may still have started the folder's session: the stop is recorded before anything more is asked, the run is stopped like any other, put back only once that session is gone, and never dispatched again. Nothing of the folder is touched while another worker is in it (the engine's session of the folder alive while this run has not asked the engine to start, or was answered `busy`): before its checkouts are made, its home switched, or anything put back, the run waits for that worker to go, whether it is starting, asking again, stopped or out of time, and it never stops that worker nor takes its session for its own. While tmux cannot say, it waits too. A stop under way is seen through before anything else of the run is read or sent. Nothing of a run is removed while its worker may still be running, whether it finished, was stopped or ran out of time: the engine names the worker's tmux session after the folder (`night-<folder>-<12 hex digits of its path's SHA-1>`, kept with the run before it is dispatched, so a crash between the engine's answer and the runner's record of it still leaves the name), and the runner ends that session itself and checks that tmux no longer has it before anything goes. It asks the tmux server the engine keeps its workers in (`tmux -L bulava` on a server, or `SUPERVISOR_TMUX_SOCKET`). This matters because the engine writes its verdict a few seconds before it lets the session go, and `night-shift stop` ends the attempt in the engine's record but leaves the session running. While tmux cannot say (it is not installed, or does not answer), the run waits and its files stay. The engine answers the same for a task it has no record of and one whose record it cannot read. A run that loses its record while its session is alive is left to work: its worker is ended only when the run is stopped or its time is out, and the run closes as stopped once the session is gone. A run still being started is taken for running whenever its kept session is alive, and is followed as such, never started again or put back under it. A record in a state engine/SERVER.md does not name, or a `running` one that does not say whether its attempt is live, is not acted on either: the run waits and keeps its files. Stopping a run, or the end of its time, stops only its own folder in Bulava; why it stopped is kept with the run before the engine is asked, so a restarted runner goes on with the same stop.

**What a run beside a ticket asks of the server.** Each Bulava worker is a Claude Code session of its own, which starts its own `browser` MCP server (`chrome-devtools-mcp --headless --isolated`, set by setup), and that server starts its own Chrome with a throwaway profile. A ticket's agent and a test run never share a browser, its tabs or its cookies. What they do share is memory: two Claude sessions, two Chromes and Codex at once take about twice what one run does, so set the key only where the machine, and any memory cap on the runner's services, has room for both. They also share whatever they both reach: a test run and a ticket that sign in to the same staging site with the same accounts, or a run that tests a dev stack in the workspace a ticket is rebuilding, see each other's changes. Give test runs accounts and data of their own in their instructions, and test a deployed stand, not the ticket's local one.

**What the agent is told.** Its brief gives the time the run is stopped and when to stop testing (an hour before, at most a quarter of the run), and asks it not to stop sooner while checks can still be done. Before testing it writes a plan to `plan.md` in its report folder, every check the instructions ask for, one line each in a set form (`- [ ] check`, under a heading per group), and marks each line as it goes by putting its result between the brackets (`- [ok] check — why`; ok, problem, blocked or skipped), so a restart or a compacted context picks up from the first line still `[ ]`. The runner counts these lines on each pass and keeps the counts with the run for its page in the console ([console.md](console.md)); it reads at most 512 KiB of the file, never through a link, and keeps none of its text. Covering most of the plan is the aim, not every line: a check the test stand cannot support (an e-mail the run cannot read, an external service not set up, a key it does not have) is marked blocked with its reason, and a check left skipped while time was left says why. Evidence shows the platform as it is: the agent never writes onto a page to photograph it, and an API response no screen shows is opened by its URL or shown raw, request and response unedited, on a blank page.

**The report.** The agent writes `findings.json` and its screenshots; the runner validates them and writes `report.html` under `qa.reports`: what was checked, and each problem with its steps, the screenshot where it went wrong, expected against actual, how often, and the suspected cause linked to the code at the commit read. Every check and every problem is an accordion: its line gives the result (or severity and type), the title and the requirement's numbers, and opening it shows the details. A check lists its cases, what was actually done for it, each with its own result (a check and its cases fit in one part of the report), under the group of the plan it belongs to (a user story, a feature); one that could not be checked or was skipped says how many of its cases were tried, or that none were, and why. Checks and problems name the requirement they are about (`spec`: the story and point as the instructions number them, and the requirement's text), so number the stories and points in the instructions for the report to cite them. A filter above the lists shows one kind at a time (findings, works, problem, could not check, skipped) with its count; it is plain HTML and CSS, as the pages run no script. Each problem also has a type the agent picks (AC, Security, UI/UX, Performance, Other; one without a known type is Other), and a second filter at the top of the problems shows one type at a time with its count. A problem check links to its finding, numbered as the report numbers it. That link, screenshots, recordings and links open in a new tab, so the reader keeps their place in the list. A check that does not list its cases, as in reports written before these fields, is marked as not listing them. A case marked as a problem with no finding to say what makes the run unfinished, as a check so marked does. What was read but is not shown as the agent wrote it (a case with no description, a link from a check that is not a problem, a link to a finding that is not there) is listed under what was left out, and does not change the outcome. The outcome is one of:

- no problems found: the run finished, the report was read whole, and at least one thing was checked with nothing left unchecked or skipped;
- no problems in what was checked, with what could not be checked or was skipped listed;
- could not test (the site down, the login refused);
- did not finish: nothing checked, everything skipped, a problem without a description, a report the runner could not read, or a run the engine ended any other way than finished; the report and Slack say why.

Bulava has Codex review the agent's report before the run ends. A test run is sent with a review of its own (engine/SERVER.md, "Review budget of a task"): at most five rounds, judged by the runner's criteria for a test report (each finding backed by its steps and a screenshot of the platform itself, never of the tester's own words, a summary that claims no more than the checks show, numbers that agree) in place of the server's rule for data changes, since test data on a test stand is expected and naming it is enough. The agent is given the same criteria in its brief. Codex reads `findings.json` itself, as it is at each round: the engine reads a report only from `artifacts/` of the folder the run works in and only as html, md or txt, so the runner links `artifacts/qa-<n>/findings.txt` to the agent's file, the agent names that link in its closing summary, and the links go when the run is over. The engine reads at most 60 000 characters of one file, so a longer report comes in parts (`findings.json`, `findings-2.json`, …, each under 40 KB), and `findings.json` then says how many parts, checks and findings there are in all; the runner checks those totals, and that the numbering has no gap. The parts are reviewed one per attempt of the task, five rounds each: once the engine ends an attempt `done`, the runner links the next part and asks the agent to finish again naming it. Answering an objection on a later part can change a part already reviewed: the totals in `findings.json` follow every part and do not count as a change, but anything else does, and once the last part is done each part changed since its review is reviewed once more the same way, its earlier objections replaced by what that review leaves. The report is published from all the parts together, with the objections left on each part under its name; a part the review never reached (the run stopped, ran out of time, or the engine did not take the next attempt), one added after the parts were counted, or one changed after its last review, is shown as not reviewed, and the run counts as one whose report did not pass its closing review. A part larger than the engine reads is a problem of the report. The engine keeps them with the task, so a run taken up again after a crash is reviewed the same way. A report Codex still objects to after the fifth round is accepted with its notes: the task ends `done`, nothing was committed, and the runner keeps the run's findings while the report, the console's list and Slack all say the report did not pass that review, with the objections Codex left unsettled shown in the report. A run sent to an older engine, which ends such a run `failed`, `needs-user`, is read the same way. The run's outcome still has to come from the report itself: one that names no check that was done (none `ok` or `problem`), or that the runner could not read whole, did not finish, findings or not. One that found no problems is never "no problems found", only "no problems found, but the report did not pass its closing review". Any other `needs-user` (an answer from Codex with no readable verdict, a review that passed but left something for a person, a commit) is still a run that did not finish. With `qa.enabled`, live mode needs an engine that takes this review (`dispatch.sh --report-criteria`, Bulava 1.20); `arceus-runner probe-bulava` shows whether it does.

**How much a report keeps.** One run keeps at most `qa.max_checks` (1000) entries of what was checked, `qa.max_findings` (300) findings, `qa.max_files` (1000) screenshots and recordings, `qa.max_media_mb` (1024) MB of them together, and a `findings.json` of `qa.max_report_mb` (8) MB. The limits guard the report page and the disk against an agent that runs away; they say nothing about how much the agent can test well, so raise them when the instructions are long. The agent is told them, and to list every check it was asked for, one entry each, the ones it did not get to as skipped. Whatever goes past a limit is left out, and the report lists it by count and by name, so such a run is never "no problems found". Each scenario's instructions are capped at 64 KiB (the brief goes to the agent as one command-line argument): split a larger test plan into several scenarios.

**How much of a text the report keeps.** The agent's own words are cut at a number of characters, each limit settable in `qa`: a check's or case's note, the reason shown when it was blocked or skipped, at `max_note_chars` (1500); the run's summary at `max_summary_chars` (1500); why it could not test at all at `max_blocked_chars` (1500); each step to reproduce a finding at `max_step_chars` (500); a finding's expected and actual, each, at `max_expected_chars` (1500); its likely cause at `max_cause_chars` (2000); and the quoted text of a requirement at `max_spec_chars` (1000). Each takes 50 to 50,000. Text past its limit ends in " …". Short labels (a check's or finding's name, a group, a caption, a file, a URL) keep fixed limits, and `findings.json` as a whole is still held to `qa.max_report_mb`.

With the web console on, the reports are its **Test runs** ([console.md](console.md)): people with the QA role (or admins) make, schedule and delete scenarios there, edit their instructions and start and stop runs, and everyone signed in reads the reports. Without it, reports are served on `127.0.0.1:3300` (`qa.port`): `ssh -L 3300:127.0.0.1:3300 <user>@<vm>`, then `http://localhost:3300/`. Either way the list is read from the database on every visit, so queued and running runs show at once, and only reports and their screenshots are served, never the instructions.

**Slack and Grafana.** The channel hears when a run starts (its scenario, and whether the schedule started it) and how it ended, with the agent's two or three lines and the report's link. On **Arceus · now** the agent shows as Testing, and the run is listed as `qa-<n>`; a run beside a ticket is listed with it, and the dashboard shows the ticket as what the runner is doing.
