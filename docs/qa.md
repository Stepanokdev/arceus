# Testing the platform

Off by default (`qa.enabled: false`). With it on, the agent tests the whole platform in a headless browser by your instructions and writes a report per run. Nothing goes through the issue tracker: no ticket, no comment; what to do about a finding is yours to decide.

**Scenarios.** Tests are organised as scenarios: any number of named test runs, each with its own instructions and its own schedule. "Smoke" on weekdays at 07:00, "Regression" on Saturday at 02:00, "Payments" only by hand. They live in the runner's database, so one made or changed in the console (**Test runs**, [console.md](console.md)) or with `arceus-runner qa scenario` counts on the runner's next pass, without a restart. At most `qa.max_scenarios` (20) exist at once. A deleted scenario stops running and leaves the list; its number is never given to another one, so its past runs and reports keep its name.

**The instructions.** A file per scenario: the platform's URL, its test accounts and what to test, in any shape. The first scenario, "Main", reads `qa.instructions` (default `~/arceus/data/qa/instructions.md`, next to the secrets). The `runner` phase copies [qa-instructions.example.md](../config/qa-instructions.example.md) there once and never overwrites it. Every later scenario has its own file beside it, `scenarios/<n>.md`, written when the scenario is made. Text inside HTML comments never reaches the agent, so the example counts as empty until you write the instructions: `arceus-runner check` fails on any scenario whose file is empty or unreadable with `qa` on, and a run of it reports it had no instructions. The runner adds how to work and how to report, and names the scenario in the brief. A run keeps the text it started with, so editing the file never changes a run under way.

**Starting a run.** In the console, **Run now** beside a scenario. On the server, `arceus-runner qa run --scenario <n>` queues one and prints its number (with only one scenario, `--scenario` can be left out); `qa status` lists the latest runs with their scenario; `qa stop [n]` stops a queued or running one (its report keeps what it found). `qa scenario list` shows every scenario with its schedule and file; `qa scenario add NAME [--days mon,fri --at 07:30]`, `qa scenario set N [--name …] [--days …] [--at …] [--by-hand]` and `qa scenario delete N` do what the console does, for an install without it.

**When scenarios run by themselves.** A scenario with days and a time is queued on those days at that time, in `schedule.timezone`; one with neither runs only when someone starts it, and one with only days or only a time is refused when saved. A scheduled time is queued once, also across restarts; one missed by more than an hour is not made up. A scenario's time that comes while a run of that same scenario is queued or under way is skipped. Runs of different scenarios queue behind each other: two scenarios due at the same minute are both queued and run one after the other, since they share the workspace, so the second starts when the first is over, which can be hours after its time. A queued run goes before new tickets, so several scenarios queued at once hold tickets back for as long as they take together: give long scenarios times when no tickets are expected. A run of a scenario deleted before it started closes without starting and says so; one under way finishes by what it was given.

**Upgrading from one instructions file.** The update makes scenario 1, "Main", from what there was: it reads `qa.instructions`, and the first time the runner starts it is given `qa.schedule`, once. From then on `qa.schedule` is not read, and `arceus-runner check` asks to remove it. Past runs become runs of "Main".

**How it runs.** A run is the Bulava task `qa-<n>`. It holds the shared workspace from start to end, and a queued run goes before new tickets. Every repository is put on a local branch `arceus-qa/<n>` at its default branch as last fetched, so the agent can name the file and line it suspects; it changes no code. A repository with uncommitted work (a ticket waiting on people) is left as it is and read with `git show`. Afterwards every repository goes back where it was. Past `qa.timeout` (8 h) the run is stopped and reported as unfinished. The run's clock starts when it is prepared, and its times are fixed then: the time it is stopped and the time its agent stops testing are kept with the run, so the brief, the runner's stop and the console's page give the same times, and a `qa.timeout` changed later applies only to runs that start after it.

**What the agent is told.** Its brief gives the time the run is stopped and when to stop testing (an hour before, at most a quarter of the run), and asks it not to stop sooner while checks can still be done. Before testing it writes a plan to `plan.md` in its report folder, every check the instructions ask for, one line each in a set form (`- [ ] check`, under a heading per group), and marks each line as it goes by putting its result between the brackets (`- [ok] check — why`; ok, problem, blocked or skipped), so a restart or a compacted context picks up from the first line still `[ ]`. The runner counts these lines on each pass and keeps the counts with the run for its page in the console ([console.md](console.md)); it reads at most 512 KiB of the file, never through a link, and keeps none of its text. Covering most of the plan is the aim, not every line: a check the test stand cannot support (an e-mail the run cannot read, an external service not set up, a key it does not have) is marked blocked with its reason, and a check left skipped while time was left says why. Evidence shows the platform as it is: the agent never writes onto a page to photograph it, and an API response no screen shows is opened by its URL or shown raw, request and response unedited, on a blank page.

**The report.** The agent writes `findings.json` and its screenshots; the runner validates them and writes `report.html` under `qa.reports`: what was checked, and each problem with its steps, the screenshot where it went wrong, expected against actual, how often, and the suspected cause linked to the code at the commit read. Every check and every problem is an accordion: its line gives the result (or severity), the title and the requirement's numbers, and opening it shows the details. A check lists its cases, what was actually done for it, each with its own result (at most 30; cases past that, or with no description, are named among what was left out), under the group of the plan it belongs to (a user story, a feature); one that could not be checked or was skipped says how many of its cases were tried, or that none were, and why. Checks and problems name the requirement they are about (`spec`: the story and point as the instructions number them, and the requirement's text), so number the stories and points in the instructions for the report to cite them. A filter above the lists shows one kind at a time (findings, works, problem, could not check, skipped) with its count; it is plain HTML and CSS, as the pages run no script. A problem check links to its finding, numbered as the report numbers it; the link shows the finding whatever the filter. That link, screenshots, recordings and links open in a new tab, so the reader keeps their place in the list. A check that does not list its cases, as in reports written before these fields, is marked as not listing them. The outcome is one of:

- no problems found: the run finished, the report was read whole, and at least one thing was checked with nothing left unchecked or skipped;
- no problems in what was checked, with what could not be checked or was skipped listed;
- could not test (the site down, the login refused);
- did not finish: nothing checked, everything skipped, a problem without a description, a report the runner could not read, or a run the engine ended any other way than finished; the report and Slack say why.

Bulava has Codex review the agent's report before the run ends. A test run is sent with a review of its own (engine/SERVER.md, "Review budget of a task"): at most five rounds, judged by the runner's criteria for a test report (each finding backed by its steps and a screenshot of the platform itself, never of the tester's own words, a summary that claims no more than the checks show, numbers that agree) in place of the server's rule for data changes, since test data on a test stand is expected and naming it is enough. The agent is given the same criteria in its brief. Codex reads `findings.json` itself, as it is at each round: the engine reads a report only from `artifacts/` of the workspace and only as html, md or txt, so the runner links `artifacts/qa-<n>/findings.txt` to the agent's file, the agent names that link in its closing summary, and the links go when the run is over. The engine reads at most 60 000 characters of one file, so a longer report comes in parts (`findings.json`, `findings-2.json`, …, each under 40 KB), and `findings.json` then says how many parts, checks and findings there are in all; the runner checks those totals, and that the numbering has no gap. The parts are reviewed one per attempt of the task, five rounds each: once the engine ends an attempt `done`, the runner links the next part and asks the agent to finish again naming it. Answering an objection on a later part can change a part already reviewed: the totals in `findings.json` follow every part and do not count as a change, but anything else does, and once the last part is done each part changed since its review is reviewed once more the same way, its earlier objections replaced by what that review leaves. The report is published from all the parts together, with the objections left on each part under its name; a part the review never reached (the run stopped, ran out of time, or the engine did not take the next attempt), one added after the parts were counted, or one changed after its last review, is shown as not reviewed, and the run counts as one whose report did not pass its closing review. A part larger than the engine reads is a problem of the report. The engine keeps them with the task, so a run taken up again after a crash is reviewed the same way. A report Codex still objects to after the fifth round is accepted with its notes: the task ends `done`, nothing was committed, and the runner keeps the run's findings while the report, the console's list and Slack all say the report did not pass that review, with the objections Codex left unsettled shown in the report. A run sent to an older engine, which ends such a run `failed`, `needs-user`, is read the same way. The run's outcome still has to come from the report itself: one that names no check that was done (none `ok` or `problem`), or that the runner could not read whole, did not finish, findings or not. One that found no problems is never "no problems found", only "no problems found, but the report did not pass its closing review". Any other `needs-user` (an answer from Codex with no readable verdict, a review that passed but left something for a person, a commit) is still a run that did not finish. With `qa.enabled`, live mode needs an engine that takes this review (`dispatch.sh --report-criteria`, Bulava 1.20); `arceus-runner probe-bulava` shows whether it does.

**How much a report keeps.** One run keeps at most `qa.max_checks` (1000) entries of what was checked, `qa.max_findings` (300) findings, `qa.max_files` (1000) screenshots and recordings, `qa.max_media_mb` (1024) MB of them together, and a `findings.json` of `qa.max_report_mb` (8) MB. The limits guard the report page and the disk against an agent that runs away; they say nothing about how much the agent can test well, so raise them when the instructions are long. The agent is told them, and to list every check it was asked for, one entry each, the ones it did not get to as skipped. Whatever goes past a limit is left out, and the report lists it by count and by name, so such a run is never "no problems found". Each scenario's instructions are capped at 64 KiB (the brief goes to the agent as one command-line argument): split a larger test plan into several scenarios.

With the web console on, the reports are its **Test runs** ([console.md](console.md)): people with the QA role (or admins) make, schedule and delete scenarios there, edit their instructions and start and stop runs, and everyone signed in reads the reports. Without it, reports are served on `127.0.0.1:3300` (`qa.port`): `ssh -L 3300:127.0.0.1:3300 <user>@<vm>`, then `http://localhost:3300/`. Either way the list is read from the database on every visit, so queued and running runs show at once, and only reports and their screenshots are served, never the instructions.

**Slack and Grafana.** The channel hears when a run starts (its scenario, and whether the schedule started it) and how it ended, with the agent's two or three lines and the report's link. On **Arceus · now** the agent shows as Testing, and the run is listed as `qa-<n>`.
